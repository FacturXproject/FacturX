F12 — Human Correction Form: Validation Rules

1. Purpose

The human correction form (page /conversion?documentId=...) lets users review and
correct the fields extracted from a PDF invoice (F11) before the invoice is used by
later processing steps (F13 generation).

Extraction is never trusted blindly: every saved draft has been checked by a human and
re-validated by the server.

2. API

GET /api/documents/{id}/draft   latest draft of the document
PUT /api/documents/{id}/draft   save the user's corrections

Both require the EXTRACT_DOCUMENT permission on the document's organisation.

PUT body:
{
  "updatedAt": "<updatedAt returned by the last GET/PUT>",   (optional, see section 7)
  "fields": { "invoiceNumber": "...", "invoiceDate": "...", ..., "vatRate": "20" },
  "lines": [ { "description": "...", "quantity": "2", "unitPrice": "10,50", "vatRate": "" } ]
}

Totals are NOT sent: the server always computes them. Totals sent anyway
(totalHt / totalVat / totalTtc) are ignored.

Editable fields (any other name is refused): invoiceNumber, invoiceDate, dueDate,
sellerName, sellerSiren, sellerVat, sellerAddress, buyerName, buyerSiren, buyerAddress,
vatRate. A field missing from the request keeps its current value.

Errors:
400 DRAFT_INVALID    { "error", "message", "errors": [every problem, in French] }
404 DRAFT_NOT_FOUND  the document has never been extracted
409 DRAFT_CONFLICT   the draft changed since it was loaded (section 7)
403 ACCESS_DENIED    no permission on the organisation

3. Required fields

The following must not be empty (whitespace only counts as empty):

Invoice number
Invoice date
Seller name
Buyer name
Default VAT rate

The invoice must have at least one line (and at most 500), and each line must have a
description.

Text values are trimmed and repeated whitespace (including line breaks) is collapsed.
A value (or line description) longer than 500 characters is refused.

4. Dates

Invoice date and due date accept DD/MM/YYYY, DD.MM.YYYY, DD-MM-YYYY (the formats the
extractor produces) and YYYY-MM-DD. The date must exist (31/02/2026 is refused).
The due date is optional, but cannot be earlier than the invoice date.

5. Numeric validation

Numbers accept French and English notation: "1 080,50", "1.080,50", "1,080.50",
"1080.5". The last separator is the decimal separator. At most 12 digits before and
6 after the decimal separator. Scientific notation ("1e3") is refused.

Quantity must be a valid number greater than zero.
Unit price must be a valid number greater than or equal to zero.
VAT rates (default and per line) must be valid numbers between 0 and 100, inclusive
(a trailing "%" is accepted).
The total including VAT must stay below 10^15 €.

Invalid numeric values are rejected.

6. Calculation rules

Each line may have its own VAT rate; an empty line rate means "use the invoice's
default VAT rate".

Line total             = quantity × unit price, rounded to 2 decimals
Total excluding VAT    = sum of line totals
VAT, for each rate     = (sum of the line totals at this rate) × rate / 100, rounded
Total VAT              = sum of the VAT of each rate
Total including VAT    = total excluding VAT + total VAT

Rounding is "half up" to two decimals (0.005 -> 0.01). With a single VAT rate this is
exactly: VAT = total excluding VAT × VAT rate / 100.

The VAT breakdown (rate, taxable amount, VAT amount) is stored in table draft_taxes and
returned as "taxes"; F13 uses it for the Factur-X tax blocks.

The frontend computes the same values (integer arithmetic, same rounding) so what the
user sees is what the server stores; the server's result is authoritative and replaces
the form's content after each save.

7. Saving, persistence and concurrent edits

The frontend validates the form before sending a save request and highlights the
fields in error. The backend independently validates the incoming data (same rules)
and recalculates totals before persisting the draft, in a single transaction: a refused
save changes nothing.

A successfully saved draft is retrievable after refreshing or reopening the page.

draft_invoices.updated_at is set on every save. The client sends back the updatedAt it
loaded; if the draft has been saved since (other tab, other member of the firm), the
save is refused with 409 instead of silently overwriting the newer correction. The
user reloads the page to get the latest version.

The page warns before leaving with unsaved changes.

8. Confidence indicators

Each field and each line shows a dot:

green   high confidence from the extractor (>= 0.6)
amber   low confidence or not found: to check
blue    corrected by the user (source "manual")

A field or line changed by the user loses its extraction confidence and gets source
"manual". Unchanged fields and lines keep their confidence and source. Computed totals
have source "calculated".
